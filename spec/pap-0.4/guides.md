# guides.md

Source: [guides.md](../source/docs/0.4/guides.md). Official page: https://personalagentprotocol.org/docs/0.4/guides

## guides.both Handling secrets

- **SHOULD** · both · `guide.access-tokens-refresh` — Access tokens and refresh tokens
- **SHOULD** · both · `guide.private-keys-client` — Private keys, client assertions, Session JWTs, and DPoP proofs
- **SHOULD** · both · `guide.authorization-codes-pkce` — Authorization codes, PKCE code verifiers, device codes, one-time sign-in codes, browser-session codes, and credentials sent in mediated sign-in
- **MUST NOT** · both · `guide.keep-logs-telemetry` — Keep them out of logs, telemetry, error reports, model context, conversation messages, and URLs. Tokens and Session JWTs MUST NOT be sent in a URL (5.6), and tokens, Session JWTs, private keys, authorization codes, PKCE code verifiers, and device codes MUST NOT go in model context (10.2)
- **SHOULD** · both · `guide.redact-authorization-poppy` — Redact the `Authorization`, `Poppy-Session`, `DPoP`, and `Cookie` headers and credential fields before a request reaches a logger or tracer
- **SHOULD** · both · `guide.send-cache-control` — Send `Cache-Control: no-store` on every response that carries a token or code
## guides.both Signing and verifying JWTs

- **MUST** · both · `guide.personal-agents-sign` — Personal agents: sign Session JWTs with ES256 (MUST, 5.2). Sign client assertions and delegations with ES256, or with PS384 if you sign them blindly (10.7). Companies: accept ES256 (MUST) and PS384 (SHOULD) in client assertions and delegations (4.1, 5.2). Use RSA keys of at least 2048 bits
- **SHOULD** · agent · `guide.personal-agents-token` — Personal agents: use `token_endpoint_auth_signing_alg_values_supported` in the Company's OAuth metadata to choose a supported client-assertion algorithm. This list does not establish support for delegation signatures. The protocol has no delegation-algorithm discovery field, and `invalid_session` does not distinguish an unsupported algorithm from other failures. An agent that requires blind signing may be unable to work with a Company that doesn't support PS384. Falling back to ES256 needs a suitable published key and gives up this blind-signing mechanism; don't switch automatically when blind signing is required by the User's privacy settings
- **SHOULD** · both · `guide.reject-none-symmetric` — Reject `alg: none` and symmetric algorithms such as HS256
- **SHOULD** · both · `guide.verify-client-assertions` — Verify client assertions and delegations only with keys from the personal agent's verified `jwks_uri` (4.1), and Session JWTs only with the key their verified delegation names in `cnf.jwk` (5.2). Ignore `jku`, `x5u`, and any other key embedded in a JWT. DPoP proofs for DPoP-bound access tokens are the one other exception: the public key in their `jwk` header is how they work
- **SHOULD** · both · `guide.check-client-assertions` — Check `aud` and `iat`, and `exp` on client assertions and delegations. Session JWTs have no `exp`: accept them only within your `iat` window (5.3). A client assertion has the company's issuer as its `aud`; a Session JWT has the Company's identifier (its issuer, or its HTTPS domain without one), never an endpoint URL (4.1, 5.2). Allow a small clock skew, such as 30 seconds, and reject assertions that claim a long lifetime
- **SHOULD** · both · `guide.make-client-assertion` — Make the `jti` of each client assertion, delegation, Session JWT, and DPoP proof at least 128 random bits, and each Session ID too
- **SHOULD** · agent · `guide.personal-agents-client` — Personal agents: set a client assertion's `exp` at most five minutes after its `iat`
- **SHOULD** · company · `guide.companies-reject-reused` — Companies: reject a reused client assertion `jti` from the same `client_id` until it expires, as RFC 7523 §3 allows
## guides.both Operator signatures and bot defenses

- **SHOULD** · both · `guide.build-request-body` — Build the request body, any DPoP proof, and Session JWT first, then the operator signature. Cover `poppy-session` and `authorization` when present, as the spec requires. Include method, authority, path, query, and a verified content digest when the verifier relies on those components
- **SHOULD** · both · `guide.keep-operator-keys` — Keep operator keys separate from delegated Session keys. Publishing every User's delegated key in an operator directory is not equivalent to verifying a delegation, and exposes a new key mapping
- **SHOULD** · both · `guide.centralized-agent-signing` — For a centralized agent, signing can happen where requests already pass. For on-device agents, sending requests to an authenticated operator signing service can reveal which Company each User visits. This signature profile does not provide blind signing. Do not send devices a shared operator private key to avoid that service
- **SHOULD** · both · `guide.verified-operator-signature` — A verified operator signature establishes control of its key source. It does not establish every client metadata URL on the same origin. Verify the Session JWT's exact `iss` before accepting it as that client, then apply Company policy and account authorization
- **SHOULD** · both · `guide.test-actual-edge` — Test the actual edge and origin together: registration, directory caching, key rotation, accepted signature components, body handling, and forwarded authentication results. Protect the origin from forged forwarding headers. A bot-verification result is not a replay check or account grant
- **SHOULD** · both · `guide.remove-extra-signature` — Remove the extra signature where an edge verifies delegated Session JWTs directly. Keep Company acceptance and all remaining Session and OAuth checks. The JWT covers method, URL without query, and access token, not the request body; do not assume removing an operator signature preserves any additional query or body protection it supplied
## guides.both Rotating keys

- **SHOULD** · both · `guide.give-every-jwks` — Give every key in `jwks_uri` a `kid`
- **SHOULD** · both · `guide.publish-jwks-before` — Publish a new key in `jwks_uri` before signing with it, early enough for companies' caches to pick it up
- **SHOULD** · both · `guide.keep-public-published` — Keep an old public key published until every client assertion and delegation signed with it has expired
- **SHOULD** · agent · `guide.personal-agents-rotate` — Personal agents: rotate delegated keys as often as you like. Each Session JWT carries its own delegation, so companies don't depend on a delegated key lasting (5.2)
- **MUST** · agent · `guide.personal-agents-rotate-2` — Personal agents: rotate DPoP keys as often as you like too, but use each one for one user ID only (MUST, 4.5). Send a proof with the new key when you refresh, and the new access token is bound to it
- **SHOULD** · company · `guide.companies-refetch-jwks` — Companies refetch `jwks_uri` when they see an unknown `kid`. The refetch happens before any signature is checked, so anyone can trigger it by naming a real personal agent and a made-up `kid`. Refetch each `jwks_uri` at most once per interval, such as 30 seconds, and count failed fetches too. Otherwise a stream of bad assertions can flood the personal agent's server
- **SHOULD** · both · `guide.rotating-signing-keys` — Rotating signing keys doesn't affect refresh tokens. They are tied to the `client_id`, not a key (4.4)
## guides.both Fetching metadata safely

- **SHOULD** · both · `guide.limits-redirects-most` — Set limits: a few redirects at most, a response size such as 100 KB, and a timeout of a few seconds
- **MUST** · both · `guide.validate-https-certificates` — Validate HTTPS certificates. Personal agents MUST follow discovery redirects only to HTTPS URLs (section 3)
- **SHOULD** · both · `guide.metadata-no-credentials` — Never send cookies, tokens, or other credentials on these fetches
- **SHOULD** · both · `guide.private-addresses` — Reject loopback, private, and link-local addresses unless you've configured them on purpose. Check the address you actually connect to, not only the one DNS returned first
- **SHOULD** · both · `guide.cache-bounds` — Cache according to HTTP caching headers, within bounds you set, such as at least a minute and at most a day. The upper bound means a removed key stops being trusted
## guides.both Explicit replies and approvals

- **SHOULD** · both · `guide.both-parties-make` — Both parties SHOULD make an answer or approval explicit about the question or action it addresses
- **SHOULD** · both · `guide.both-parties-treat` — Both parties SHOULD treat a short reply that could answer more than one open question as answering none of them, and ask which one is meant before acting. A reply such as "done" could refer to sign-in, an earlier question, or a new request for approval
## guides.both Retries

- **SHOULD** · both · `guide.send-idempotency-draft` — Send an `Idempotency-Key` (draft-ietf-httpapi-idempotency-key-header) on API writes that accept one. Use a random UUID (version 4), and reuse the same key when you retry the same request
- **SHOULD** · both · `guide.give-conversation-request` — Give each conversation request, such as a message or a handoff request, an `id` with at least 128 random bits, and reuse it when you retry the request (8.3)
- **SHOULD** · both · `guide.retry-needs-session` — Each retry needs a new Session JWT, and a new DPoP proof if the access token is DPoP-bound. A retried token request needs a new assertion. The company may reject a `jti` it has already seen
- **MUST** · both · `guide.wait-least-long` — Wait at least as long as `Retry-After` says on a 429 (MUST, 5.6) or a 503
- **SHOULD** · both · `guide.otherwise-back-exponentially` — Otherwise, back off exponentially with jitter, cap the delay, and limit the number of attempts
- **SHOULD** · company · `guide.companies-keep-idempotency` — Companies keep idempotency records for a set time, such as a day, scoped to the personal agent's `client_id` and the user ID, and to the account when there is one, not to the session, so a retry in a new session still matches. They return the original response for a repeated key, and reject a repeated key with a different body
## guides.both Rate limits

- **SHOULD** · company · `guide.companies-limit-client` — Companies: limit by `client_id`, by user, and by session, so one busy personal agent or user doesn't crowd out others. Count a request against a `client_id` only after its Session JWT or client assertion's signature checks pass. Otherwise anyone can name a personal agent and use up its limit, so its real users are refused. Limit unverified requests by network instead
- **SHOULD** · company · `guide.companies-send-ratelimit` — Companies: also send the `RateLimit` and `RateLimit-Policy` headers (IETF draft), so personal agents can slow down before they hit a limit
- **SHOULD** · agent · `guide.personal-agents-keep` — Personal agents: keep track of limits for each company and share them across your tasks and users, rather than letting each task find the limit on its own
- **SHOULD** · agent · `guide.personal-agents-prefer` — Personal agents: prefer long polling or streaming over repeated short polls, and check for changes no more often than the task needs. Checking once a day for a price drop is usually enough
- **SHOULD** · agent · `guide.personal-agents-work` — Personal agents: run work that isn't time-sensitive, such as checking order status in the background, outside the company's busy hours, and spread it out instead of starting it all at the same moment
## guides.both Transport and JSON

- **SHOULD** · both · `guide.later-prefer` — Use TLS 1.2 or later. Prefer TLS 1.3
- **SHOULD** · both · `guide.encode-json-reject` — Encode JSON as UTF-8 and reject objects with duplicate member names
- **SHOULD** · both · `guide.write-timestamps-3339` — Write timestamps in RFC 3339 with a time zone offset, such as `2026-10-02T17:15:00-07:00`
- **SHOULD** · both · `guide.ignore-fields-recognize` — Ignore fields you don't recognize, so later versions can add them
## guides.agents User IDs

- **SHOULD** · agent · `guide.store-random-user` — Store a random ID for each user and company the first time they're needed. This is the simplest choice
- **SHOULD** · agent · `guide.derive-keyed-hash` — Derive one with a keyed hash, such as HMAC-SHA256 of your internal user ID and the company's identifier (its issuer, or its HTTPS domain without one), with a secret key. Changing the key changes every ID, so the company sees all your users as new
- **SHOULD** · agent · `guide.create-random-anonymous` — Create a random ID for each anonymous browsing session. Its sessions have their own `sid`, and its delegated keys sign for no other user ID (5.2), so nothing links it to the user's other sessions
- **SHOULD** · agent · `guide.discard-browsing-session` — Discard the ID when the browsing session ends. Carts and conversations from it end with it
- **MUST NOT** · agent · `guide.never-send-access` — Never send an access token with an anonymous ID (MUST NOT, 5.4). If the user wants to sign in, switch to their regular ID in a new session
## guides.agents The Session header

- **SHOULD** · agent · `guide.decide-where-send` — Decide where to send the header from the company's `poppy.json` and its listed API descriptions (5.2). For OpenAPI, resolve the request URL from the operation's server and path. For MCP, use the listed server endpoint and its transport's request URLs. For conversations, use the listed endpoint and the routes in 8.2. Other protocol and extension endpoints follow their definitions, such as `tasks.endpoint`, the `feedback.endpoint` its response lists, and `{browser_session_endpoint}/authorize`. Match the request to those operations and routes before signing. A host allowlist alone would include unrelated paths on a shared host
- **SHOULD** · agent · `guide.fetch-discovery-documents` — Fetch discovery documents, API descriptions, and other public documents without the Session header. Keep it off OAuth requests too. A web link in an alternative or message doesn't add a destination. The JWT's `aud` identifies the company, while `htu` binds it to the request URL. Neither chooses where to send it
- **SHOULD** · agent · `guide.fetch-website-page` — When you fetch a website page yourself, without a browser, send the header if the page is on the host that served `poppy.json` (SHOULD, 5.2), never with an access token. Sign a new one for a redirect only while it stays on that host. A browser, headless or not, joins the session instead (section 6)
- **SHOULD** · agent · `guide.page-answers-invalid` — If a page answers `invalid_session`, treat it as a bug in your header, as at any endpoint, and check the JWT. You can fetch the page again without the header in the meantime (5.2)
- **MUST** · agent · `guide.choose-session-random` — Choose each session's `sid` at random, and never use it for another session (MUST, 5.2). Keep it for as long as you use the session: it names the session, so a lost `sid` means a new session
- **MUST** · agent · `guide.send-same-agent` — Send the same `sub` and `agent_id` in every Session JWT for a session (MUST, 5.2)
- **MUST NOT** · agent · `guide.sign-session-request` — Sign a new Session JWT for each request, in an HTTP client hook that sees the final method and URL. Don't let the client follow redirects from protocol endpoints with the Session header or a token: you MUST NOT send either to the new URL (section 3)
- **MUST** · agent · `guide.generate-delegated-keys` — Generate delegated keys where you sign, and make them non-extractable where your platform allows, such as in a key management service, WebCrypto, or the device's keystore. Use each one for one user ID only (MUST, 5.2)
- **MUST NOT** · agent · `guide.delegation-before-current` — Get a new delegation before the current one expires. You MUST NOT sign a Session JWT after its delegation's `exp` (5.2). Round its `iat` down, such as to the start of the hour, and set `exp` from the rounded value, so delegations issued together can't be matched by their times. Keep its lifetime to a few hours
- **SHOULD** · agent · `guide.never-expose-private` — Never expose private keys to a model or to tools a model can call. Sign on the model's behalf in code it can't reach
- **MUST** · agent · `guide.request-gets-session` — When a request gets `session_ended`, start a new session with a new `sid` and send the request again (MUST, 5.5). The old session's cart and browser cookie don't carry over, so tell the user if a cart is lost. On `invalid_session`, don't start a new session: it would fail the same way. Check the JWT instead, such as its delegation's `exp`, `htu`, and the clock
- **SHOULD** · agent · `guide.company-issues-dpop` — If a company issues DPoP-bound access tokens, also sign a DPoP proof for each request that carries one, and support nonces as RFC 9449 §8 describes. The proof and the Session JWT are separate signatures with separate keys (5.2)
## guides.agents Storing tokens

- **SHOULD** · agent · `guide.store-refresh-tokens` — Store refresh tokens as secrets (10.2). Encrypt them at rest, apart from the model and its tools. Give tools a reference to the token, not the token
- **SHOULD** · agent · `guide.keep-access-tokens` — Keep access tokens in memory and drop them when they expire
- **SHOULD** · agent · `guide.refresh-token-tied` — A refresh token is tied to your `client_id`, not to a DPoP key (RFC 9449 §5), so whoever holds it and your client private key can use it. Keep the client private key in a key service or hardware security module that signs without exporting it, and store refresh tokens apart from it
- **SHOULD** · agent · `guide.store-refresh-tokens-2` — Store refresh tokens by the company's full issuer, as for user IDs, so a token from one company hosted by a provider is never sent to another
- **SHOULD** · agent · `guide.before-first-signed` — Before the first signed-in call to a service, fetch its protected resource metadata. If it has some and its `resource` isn't `https://{organization.domain}`, request a token for that `resource` and use that token only there (4.5). Cache the metadata by its HTTP caching headers, and fetch it again when the service answers `invalid_token` with `resource_metadata`
- **MUST** · agent · `guide.server-always-token` — At an MCP server, always use a token whose `resource` is the server's `url` (MUST, section 7), with the scheme `token_type` names. Send the Session header there too: the server may ignore it, but you can't tell in advance
- **MUST** · agent · `guide.company-returns-refresh` — When the company returns a new refresh token, you MUST use it from then on (4.4). Replace the stored one right away. When a refresh response omits it, keep the existing refresh token
- **SHOULD** · agent · `guide.after-user-signs` — After the user signs in again for more scopes, revoke the old refresh token (4.7)
- **SHOULD** · agent · `guide.invalid-grant-refresh` — On `invalid_grant` for a refresh token, continue signed out: send the Session header without an access token (5.5)
- **SHOULD** · agent · `guide.session-second-account` — Use a new session for a second account (5.4), keeping its tasks and browser cookie separate from the first account's
## guides.agents Choosing how to sign in

- **SHOULD** · agent · `guide.before-asking-user` — Before asking the user to sign in, check whether a refresh token you hold already covers the task (5.4)
- **MUST** · agent · `guide.offer-sign-company` — Don't offer sign-in at a company that sets `auth.disabled` (MUST, 3.2). When a company refuses a sign-in type with `unauthorized_client`, continue signed out, tell the user the company doesn't offer that sign-in to you, and remember the refusal for a while rather than asking the user again on the next task (4.1)
- **SHOULD** · agent · `guide.prefer-direct-device` — Prefer direct or device sign-in to mediated sign-in (SHOULD, Mediated Sign-In 6), and direct to device sign-in (SHOULD, 4). With direct and device sign-in, the user's password stays with the company
- **SHOULD** · agent · `guide.scopes-supported-issuer` — Use `scopes_supported` from the issuer's metadata and from the domain's protected resource metadata, the company's OpenAPI description, and its sign-in extension metadata to find scopes. The advertised list may be incomplete. Read descriptions where available to pick the ones the task needs (4.7); a missing description or hint says nothing about whether a scope is safe to request automatically
- **SHOULD** · agent · `guide.auth-scope-hints` — Use `auth.scope_hints` to decide which scopes need the user's go-ahead before you request them (4.7). For example, request a scope whose `changes` is `irreversible`, or whose `personal_data` is `true`, only when the user agreed to that kind of access, and let the user set that preference once rather than for every sign-in. Treat a scope without hints as `irreversible` with personal data
- **SHOULD** · agent · `guide.hints-describe-whole` — Hints describe a whole scope. The consequences of one action still come from the action itself, such as an MCP tool's annotations, or the HTTP method: a `GET` doesn't change anything
- **SHOULD** · agent · `guide.fewest-scopes-task` — Ask for the fewest scopes the task needs, not every scope the company offers. For a task that only looks things up, request a read-only access token with a broader refresh token (4.4)
- **SHOULD** · agent · `guide.user-approve-fewer` — The user may approve fewer scopes than you asked for. Check `scope` in the response before continuing. A response without `scope` granted every scope you asked for
- **SHOULD** · agent · `guide.company-grant-scope` — A company may also not grant a scope to this user at all, for example when only the account holder can allow an action (4.7). You can't tell that apart from the user leaving it out. When a sign-in comes back without a scope the task needs, don't send the user to sign in again just for it. Tell them that access wasn't granted, and that if they didn't leave it out, someone else on the account, such as the account holder, may need to do the task
## guides.agents Direct and device sign-in

- **MUST** · agent · `guide.direct-device-sign` — Use direct or device sign-in only when the user signs in themselves (MUST, 5.4). Never type the user's password, enter their one-time code, or click the company's approval controls for them
- **SHOULD** · agent · `guide.open-authorization-user` — Open the authorization URL in the user's own browser, not in a browser you automate
- **MUST** · agent · `guide.make-state-random` — Make `state` random and single-use. Record which company it belongs to, and exchange the code only at that company's `token_endpoint`. Check that the redirect's `iss` matches that company's issuer (MUST, 4.2)
- **SHOULD** · agent · `guide.pkce-code-challenge` — Use PKCE with `code_challenge_method=S256`, as RFC 9700 §2.1.1 recommends
- **SHOULD** · agent · `guide.receive-redirect-device` — If you can't receive the redirect on the device the user is talking to you on, send the authorization URL to the user, for example to their phone, with a redirect URI you control. Fall back to device sign-in only when that isn't possible (4.3)
- **MUST** · agent · `guide.device-sign-show` — For device sign-in (4.3), show `verification_uri_complete` as a link or QR code, and show `user_code` too so the user can confirm it matches. Keep `device_code` private. Show the link only if its host is the company's issuer host or `organization.domain`, or a subdomain of either, and show the company's name and domain with it (MUST, 4.3)
- **SHOULD** · agent · `guide.poll-faster-interval` — Poll no faster than `interval`. On `slow_down`, add 5 seconds to the interval, as RFC 8628 describes
## guides.agents Mediated sign-in

- **SHOULD** · agent · `guide.collect-extension-fields` — Collect the extension's `fields` in a form that sends them straight to your sign-in code, so secret values never pass through the model
- **MUST** · agent · `guide.look-stored-credentials` — Look up stored credentials by the company's issuer, and show the company's name and domain on the form and when asking for a code (MUST, Mediated Sign-In 6). Field labels come from the company and can name anything
- **MUST** · agent · `guide.secret-fields-never` — Secret fields MUST never be shown back to the user, logged, or sent anywhere other than the token endpoint of the company's issuer (Mediated Sign-In 2)
- **MUST** · agent · `guide.after-sign-ends` — After a sign-in ends, you MUST either discard the credentials or keep them only in a credential store the user chose, such as a password manager (Mediated Sign-In 6). If you discard them and the user needs to sign in again later, ask again
- **SHOULD** · agent · `guide.after-user-disconnects` — After the user disconnects you or the company revokes your access, don't sign in again with stored credentials unless the user asks you to
- **SHOULD** · agent · `guide.code-required-tell` — On `code_required`, tell the user where the code was sent, using `sent_to`, ask for it, and send only the code with `sign_in_id` (Mediated Sign-In 4)
## guides.agents Native and distributed apps

- **SHOULD** · agent · `guide.signing-private-distribute` — Don't put your signing private key in an app you distribute. Anyone could extract it and act as your personal agent. Keep the key on your server, and have the app ask the server to sign assertions for the signed-in user
- **SHOULD** · agent · `guide.delegated-keys-stay` — Delegated keys can stay on the device. The app generates one in its platform keystore and asks your server for a delegation for it, then signs Session JWTs itself (5.2). 10.7 explains what this hides from your own servers, and blind signing, which hides more
- **SHOULD** · agent · `guide.redirect-uris-https` — Redirect URIs are HTTPS URLs on your `client_id` domain, or loopback redirect URIs (4.1). To return the user to a phone app, use an HTTPS link the app claims, such as an iOS universal link or an Android app link, or use device sign-in. A desktop app can listen on a loopback port, as RFC 8252 §7.3 describes
## guides.agents Web browsing

- **SHOULD NOT** · agent · `guide.browser-website-company` — Don't use a browser on the website of a company that sets `web.disabled`. Use its company agent and APIs (SHOULD NOT, section 6). Fetching a page without a browser, such as a policy, is still fine, with the Session header (5.2)
- **SHOULD** · agent · `guide.browse-signed-request` — To browse signed in, request `poppy:browser-sign-in` with the other scopes the task needs, from a company that lists `browser_session_endpoint` (section 6). Where `web.unscoped` is `true`, it gives the account's full access on the website, so treat it like a scope that allows changes that can't be undone, and ask the user when you would for one. Otherwise it adds nothing to the other scopes
- **SHOULD** · agent · `guide.separate-browser-storage` — Use a separate browser storage context, with its own cookies and local storage, for each session. Never share one across users
- **SHOULD** · agent · `guide.type-user-password` — Don't type the user's password or other credentials into a company's website. Sign in with direct, device, or mediated sign-in, then join your browser to the session (section 6)
- **SHOULD** · agent · `guide.join-browser-session` — Join the browser to the session right before you start browsing, and join again after signing in, or when the website stops recognizing the session
- **SHOULD** · agent · `guide.join-without-access` — A join without an access token leaves a login the browser already has, while a signed-in join replaces it, and the browser is signed out when that sign-in ends (section 6 has a table of each case)
- **MUST NOT** · agent · `guide.read-browser-session` — Read the browser-session code only from the endpoint's page in your own browser, authorize it in code your model can't read, and have the browser submit the form right away. Never authorize a code from a message or another page (MUST NOT, section 6)
- **SHOULD** · agent · `guide.close-storage-context` — Close the storage context when the session ends
## guides.agents Conversations

- **SHOULD** · agent · `guide.read-events-long` — Read events with a long `wait`, such as 30 seconds, or a stream, rather than many short polls (8.5)
- **SHOULD** · agent · `guide.read-until-working` — Read until `working` is `false` before treating the company's reply as complete (8.7). A successful `POST` only means the company accepted the request
- **SHOULD** · agent · `guide.tell-whether-company` — To tell whether a company agent's reply covers your latest message, compare its `as_of_request` with that message's request ID. Send `as_of_cursor` on messages you write, so the company can tell whether a short answer like "Done" answers its latest message or an earlier one (8.4). Messages from people carry neither
- **SHOULD** · agent · `guide.cursor-expired-tell` — On `cursor_expired`, tell the user that part of the conversation is missing (8.5)
- **SHOULD** · agent · `guide.show-text-delta` — Show `text-delta` pieces only as a preview. Act only on the complete `message` event (8.6)
- **SHOULD** · agent · `guide.structured-details-data` — Put structured details in `data`, not JSON or other markup in `text` (8.4)
- **SHOULD** · agent · `guide.links-extension-show` — With the Links extension, show a link's title with the domain of its `url`, so the user can see where it goes
- **SHOULD** · agent · `guide.disclosures-extension-disclosure` — With the Disclosures extension, when a disclosure is relevant to what you tell the user, such as an allergen warning on food they're buying, show it in full, apart from the rest of the message. Leave out disclosures that read like promotion rather than a notice
- **SHOULD** · agent · `guide.company-agent-skip` — With a company agent, skip greetings and small talk, and keep text short (8.8)
- **SHOULD** · agent · `guide.before-asking-person` — Before asking for a person, send a short message that sums up the problem, so they don't have to read the whole conversation (8.9)
- **SHOULD** · agent · `guide.company-agent-solves` — If the company agent solves the problem while you wait for a person, withdraw the request with `handoff/cancel`. Then follow `handoff` and `responder`: the company may still assign someone (8.9)
- **SHOULD** · agent · `guide.person-takes-over` — When a person takes over, write for them: concise, plain sentences, details in `text` rather than only in `data`, and time to reply
- **SHOULD** · agent · `guide.close-conversation-task` — Close a conversation when the task is done, after reading until `working` is `false`. The company may drop requests it hasn't acted on when the close arrives (8.12)
- **SHOULD** · agent · `guide.user-accepts-user` — When the user accepts a `user_requested` invitation, start the direct conversation with `parent_conversation_id` and `user_requested_event_id`. Omit `message` to let the company speak first (8.10). Keep reading or streaming its events while the user is participating, including when the user hasn't sent a message
- **SHOULD** · agent · `guide.user-returns-control` — When the user returns control to the personal agent, close their direct conversation before continuing in the parent (8.10). Merely switching away from the direct conversation needn't close it
- **SHOULD** · agent · `guide.company-agent-asks` — If a company agent asks in a message for a one-time code, or for details to verify the user, such as a date of birth or part of an account number, ask it to request sign-in with an `authorization` event instead (8.11). Don't send codes in messages (Handling secrets)
- **SHOULD** · agent · `guide.some-oauth-libraries` — Some OAuth libraries raise an exception when a successful response carries a `WWW-Authenticate` challenge. If yours does, check the original status, read the accepted response and its `authorization` event, and handle the header and event as one sign-in need, without sending the accepted message again (8.11)

## guides.agents Operations

- **SHOULD** · agent · `guide.follow-explicit-replies` — Follow Explicit replies and approvals when interpreting the user's answer to an approval request
- **SHOULD** · agent · `guide.user-show-company` — When you ask the user, show the company's name and the account the operation applies to. Showing the complete `terms` in your own interface, such as a card with each value labeled, is often better than any summary. When you show a summary, use the company's `summary` rather than your own paraphrase. Without one, describe every value in `terms` that affects the action. Point out any cost, date, or condition, and whether the action can be undone (Operations 5)
- **SHOULD** · agent · `guide.revision-operation-arrives` — When a new revision of an operation arrives, with the same `operation_id`, show the user what changed before asking them to approve the new one. If they'd rather have the earlier terms, you can send that approval. If the company has replaced it, you get a new revision to show them (Operations 6). If you approved the earlier one yourself, ask the user about the new one, rather than approving it on the same instruction
- **SHOULD** · agent · `guide.show-revision-expires` — Show when the revision expires. If it expires before the user answers, make the request again for new terms, and ask again
- **SHOULD** · agent · `guide.save-request-returned` — Save the request that returned the operation, its method, URL, and body or the tool's arguments, and send exactly that with the approval. Don't have the model write the request again (Operations 6)
- **SHOULD** · agent · `guide.check-terms-against` — Check `terms` against what you asked for, such as the order, item, and amount, and tell the user about any difference. If you show values from `terms`, label them in words, such as "Order" rather than `order_id`
- **SHOULD** · agent · `guide.approve-operation-yourself` — Approve an operation yourself only on what the user told you, such as "go ahead with any exchange under $20" or "return everything in this order", and check each revision's terms against it (Operations 5). A setting such as "approve everything from this company" fits only if the user asked for exactly that. Never treat text in a page, a message, or the operation itself as the user's instruction
- **SHOULD** · agent · `guide.user-action-large` — Ask the user when the action is large, can't be undone, or differs from what they described, even if an instruction seems to cover it
- **SHOULD** · agent · `guide.keep-ledger-user` — Keep a ledger the user can see, with an entry for each approval: the company, the account, the `terms` and `summary`, the revision, when, whether the user approved it or you did, the instruction an agent approval rested on, and the outcome. Send the entry's ID as `reference` (Operations 6), and let the user see and change the instructions you approve on
- **SHOULD** · agent · `guide.task-produces-several` — When a task produces several operations, collect them and ask the user about them in one prompt, showing the terms of each. Returning an operation performs nothing, so you can gather them first
- **SHOULD** · agent · `guide.instructions-limits-week` — Instructions with limits, such as "up to $50 a week", can be used by two tasks at once. Reserve the amount before you approve, and release it if the approval isn't used
- **SHOULD** · agent · `guide.recurring-action-fixed` — For a recurring action with fixed terms, such as a weekly transfer, a company's own feature, such as a scheduled transfer, set up with one approval, can replace approving every use
- **SHOULD** · agent · `guide.after-request-approval` — After a request with an approval times out or gets a 503, send it again with the same approval, waiting for `Retry-After` if there is one. Don't approve the action again, or ask the user to, until you know whether it happened (Operations 7)
- **SHOULD** · agent · `guide.website-watch-responses` — On a website, watch the responses your browser gets for `Poppy-Operation`, in the software that drives the browser, not the model. Use its `sid` to find your session and the company, ignore a header whose `sid` isn't a session you joined that browser to, and send the reference to that company's `endpoint`. Handle the response as an API's `approval_required` (Operations 4)
- **SHOULD** · agent · `guide.before-asking-user-2` — Before asking the user about an operation from a website, check that it's for the action your browser just took. A script on the page can make the website return another one (Operations 8.2)
- **SHOULD** · agent · `guide.after-company-records` — After the company records the approval, have the browser repeat the action, such as by pressing the page's Continue button or the same button as before, unless the page already moved on by itself (Operations 6)
- **SHOULD** · agent · `guide.repeating-action-gets` — If repeating the action gets a new reference, look up the earlier one first. Don't ask the user about the new operation while the earlier one is `performing`, or once it's `performed` (Operations 7)
## guides.companies Choosing capabilities

- **SHOULD** · company · `guide.signed-apis-expose` — Signed-out APIs. You can expose a catalog or other stateless API without an OAuth server. Accept the Session header personal agents send. If the endpoint uses no Session claims, it can serve requests without verifying the header (5.3)
- **SHOULD** · company · `guide.session-continuity-verify` — Session continuity. Verify Session JWTs when you want to recognize a pseudonymous user, maintain a Session cart, or connect activity across channels. Verification is required before relying on Session identity, ownership, continuity, or state (5.3). This works without OAuth
- **SHOULD** · company · `guide.account-access-oauth` — Account access. Add OAuth when tasks need access to a user's account. Your endpoints can rely on OAuth alone if they use no Session claims. They still validate tokens and enforce scopes and any required DPoP checks. Check your existing authorization server against what Poppy adds to OAuth and client metadata support. Check `protected_resources` in its metadata first (3.2): it's the required field an existing issuer is most likely to be missing, and adding it may need a release from its vendor
- **SHOULD** · company · `guide.channels-other-capabilities` — Channels and other capabilities. Offer APIs, web browsing, conversations, or a combination. Add browser join to connect website activity to a Session. Advertise excluded tasks, feedback, and extensions where they help users complete the tasks you support
## guides.companies Verifying personal agents

- **MUST** · company · `guide.fetch-client-without` — Fetch the `client_id` URL without following redirects. Its `client_id` MUST equal the URL you fetched (4.1)
- **SHOULD** · company · `guide.cache-client-metadata` — Cache client metadata and key sets, as described in Fetching metadata safely
- **SHOULD** · company · `guide.keep-allowlists-blocklists` — Keep allowlists or blocklists of `client_id` values, and rate-limit session creation and new `client_id` values (4.1)
- **SHOULD** · company · `guide.client-metadata` — Check whether your authorization server supports client ID metadata documents. Some do, some support them only for clients an administrator registers by URL, and some don't yet. If yours needs registration, register the personal agents you accept by their `client_id` URL and reject others with `invalid_client`, which 4.1 allows. Your OAuth integration can fetch and check the metadata document. Your resources also fetch it when verifying Session JWTs (5.3)
- **SHOULD** · company · `guide.authorization-server-accepts` — If your authorization server accepts client ID metadata documents, publish `client_id_metadata_document_supported: true` in its metadata, as the CIMD draft §8 defines, so other clients, such as MCP clients, can tell. Personal agents don't need it: a company that offers sign-in already reads their metadata documents (4.1)
## guides.companies Verifying the Session header

- **SHOULD** · company · `guide.verify-session-header` — Verify the Session header in one place, such as a gateway in front of your APIs, conversation endpoint, and browser-session `/authorize` endpoint, and pass the verified `client_id`, `sid`, user ID, and agent ID to the services behind it
- **SHOULD** · company · `guide.cache-verified-delegations` — Cache verified delegations until they expire (5.2). Key the cache by a hash of the whole delegation, such as its SHA-256, not by its `jti`, which a forged delegation could copy. Most requests then need one signature check
- **SHOULD** · company · `guide.behind-proxies-load` — Behind proxies and load balancers, compare `htu` with the public URL the personal agent used. Build it from your configured public origin, not from the `Host` header your server receives
- **SHOULD** · company · `guide.dpop-window` — Use an acceptance window of about one minute for `iat`, plus a small clock skew
- **SHOULD** · company · `guide.rejecting-reused-optional` — Rejecting a reused `jti` is optional, as it is for DPoP proofs, because servers behind one endpoint don't always share state. Without it, a copied Session JWT still works only for the same method and URL, with the same access token, and within the acceptance window. A request that changes something then relies on being idempotent, so a replay doesn't repeat it. Conversation requests already are, through their IDs (8.3)
- **SHOULD** · company · `guide.keep-replay-cache` — If you keep a replay cache keyed by `jti`, hold entries for the acceptance window and share it across every server. Otherwise a JWT accepted by one server can be replayed at another (5.3)
- **MUST** · company · `guide.check-against-access` — Check `ath` against the access token, and that the token was issued to the JWT's `iss`. Reject an absent header when the request depends on Session claims (MUST, 5.3). Don't use an unverified `iss`, `sub`, or `sid` for attribution, rate limits by identity, cache keys, or state lookup
- **SHOULD** · company · `guide.return-invalid-session` — Return `invalid_session` for a failed check, and keep access token errors in `WWW-Authenticate`, as OAuth does (section 7)
- **SHOULD** · company · `guide.binding-access-tokens` — Binding access tokens with DPoP is your choice (4.5), and you can choose for each service. If you do, verify the proof as RFC 9449 describes, separately from the Session JWT. For a service that doesn't verify proofs, such as an MCP server built for ordinary MCP clients, have your authorization server issue Bearer tokens for its `resource`. If your authorization server can't issue DPoP-bound tokens, verifying the Session JWT and its `ath` binds the token to the personal agent's key. Endpoints that skip Session verification lose that extra protection
- **MUST** · company · `guide.server-accept-token` — At an MCP server, accept a token issued for its `resource` only at that server (MUST, section 7). Accept the Session header there too, if you want its calls tied to sessions. Signed-out calls that use no Session state can work without verification
- **SHOULD** · company · `guide.pages-host-serves` — Pages on the host that serves your `poppy.json` can get the Session header too, from personal agents that fetch them without a browser, and never with an access token (5.2). Verify it before using it, for example to recognize the personal agent or to keep the request in its session. Treat the request as signed out, even when the session's browser is signed in. When the check fails, return `invalid_session` as at any endpoint (5.3), so the personal agent can find the mistake
- **SHOULD** · company · `guide.serve-personal-agent` — Serve personal agent conversations only from your conversation endpoint (8.2). If your website chat or other channels can open the same conversations, they may not check the Session header, and anyone with a copied token could read them there
## guides.companies Sessions

- **SHOULD** · company · `guide.behind-load-balancer` — Behind a load balancer, share session state across the servers that handle it, as with server-side cookie sessions, so requests reach the same state whichever server handles them
- **SHOULD** · company · `guide.record-user-agent` — Record the user ID and agent ID a session starts with, and reject later Session JWTs for it with different ones (5.3)
- **SHOULD** · company · `guide.session-verification-needs` — Session verification needs no state until the session lookup, so a gateway in front of your endpoints can verify the header once and pass the verified claims on. Endpoints that use no Session claims don't need to change (5.3)
- **SHOULD** · company · `guide.authorization-server-session` — Your authorization server doesn't see the Session header. Sign-in and refresh are plain OAuth, and a session is signed in on each request that carries an access token (5.4)
- **SHOULD** · company · `guide.remember-sessions-answer` — Remember the `sid`s of sessions you end, and answer them with `session_ended` (5.5). Choose a retention period that fits your session lifetimes
- **SHOULD** · company · `guide.separate-sessions-separate` — Use separate sessions for separate accounts. If your policy refuses a second account in a session, answer with `session_ended` (5.4)
- **MUST NOT** · company · `guide.expect-user-delegated` — Don't expect a user's delegated key to stay the same (MUST NOT, 5.2). You can reject a delegated key that signs for a second user ID while a delegation for it lasts, which limits a leaked key to one user (10.7)
## guides.companies Token lifetimes and sign-out

- **SHOULD** · company · `guide.give-access-tokens` — Give access tokens a lifetime of hours, not days
- **SHOULD** · company · `guide.sign-invalidate-access` — At sign-out, invalidate the access tokens issued under the revoked refresh token, as RFC 7009 §2.1 describes, or check on each request whether the authorization is still active, so sign-out takes effect right away. If you can do neither, keep access tokens to a few minutes (5.5)
- **SHOULD** · company · `guide.stop-accepted-work` — Don't stop accepted work because the access token that started it expired. A job can outlast the token
- **SHOULD** · company · `guide.revoke-stops-work` — Where work in progress can take consequential actions on the user's account, such as payments or changes that are hard to undo, tie it to the refresh token, so revoking access stops it right away
- **SHOULD** · company · `guide.give-refresh-tokens` — Give refresh tokens a lifetime that fits the account, such as 90 days, and expire ones that go unused sooner. Keep it long enough that users don't have to sign in again often
- **SHOULD** · company · `guide.revoke-user-refresh` — Revoke a user's refresh tokens when they reset their password or you suspect the account is compromised
- **SHOULD** · company · `guide.consider-issuing-refresh` — Consider issuing a new refresh token on each refresh and revoking the grant when an old one is used again, as RFC 9700 §4.14.2 describes. If a refresh token is copied, the grant ends as soon as both copies have been used
- **SHOULD** · company · `guide.personal-agent-signing` — If a personal agent's signing key may have leaked, revoke every refresh token issued to its `client_id`. Its refresh tokens are tied to the `client_id`, not to a DPoP key (RFC 9449 §5)
## guides.companies Describing scopes

- **SHOULD** · company · `guide.what-scope-lets` — Say what the scope lets the personal agent see or do, in words a user understands
- **SHOULD** · company · `guide.specific-enough-model` — Be specific enough for a model to match a task to the scopes it needs. "See your orders and returns" works better than "Read access"
- **SHOULD** · company · `guide.whether-scope-reads` — Say whether the scope only reads, and whether a write scope also allows reading
- **SHOULD** · company · `guide.words-actions-undone` — Say in words which actions can't be undone and what personal data the scope shows
- **SHOULD** · company · `guide.give-scope-hints` — Give each scope its hints in `auth.scope_hints` (4.7). Judge each scope by the most consequential operation that requires it: one operation that can't be undone makes the whole scope `irreversible`. When you're unsure about a scope, leave it out of `auth.scope_hints` rather than guess
- **SHOULD** · company · `guide.splitting-scope-earn` — Splitting a scope can earn it a better hint. A personal agent may request `orders:read` freely but ask the user first before requesting a scope that can cancel orders
## guides.companies Describing APIs

- **SHOULD** · company · `guide.clearly-what-operation` — Say clearly what each operation does and when to use it, in terms of the user's task
- **SHOULD** · company · `guide.keep-small-whole` — Keep them small. The whole description takes room in the model's context, so leave out what personal agents don't need, such as long examples or operations only your own apps call
## guides.companies Consent pages

- **SHOULD** · company · `guide.start-heading-names` — Start with a heading that names the personal agent and says it wants to connect to the user's account, such as "Muse wants to connect to your Example account". Show it on your sign-in page too, before the user signs in, since that's where they decide whether to go on. Word it as connecting, not as "Sign in with Muse", which reads as signing in with a Muse account
- **SHOULD** · company · `guide.user-sign-passkey` — Let the user sign in with a passkey or another phishing-resistant method, as on your website. Direct and device sign-in happen on your own pages, so passkeys work there. They can't work with mediated sign-in, where the personal agent collects the credentials. A passkey protects against fake sign-in pages, but not against a user approving a sign-in someone else started, so the advice on this page and for device sign-in still applies
- **SHOULD** · company · `guide.show-personal-agent` — Show the personal agent's name and logo, and the domain of its `client_id`. The personal agent chooses its own name, so the domain is what the user can trust
- **SHOULD** · company · `guide.tell-user-continue` — Tell the user to continue only if they just asked that personal agent to connect, such as "Only continue if you asked Muse to do this just now." Anyone can start a sign-in and send the user the link, and nothing in the request says who started it. A user who doesn't use that personal agent, or didn't ask, can then decline
- **SHOULD** · company · `guide.show-account-being` — Show the account being connected, the requested scopes in plain language, and how long access lasts. Group related scopes rather than listing their names
- **SHOULD** · company · `guide.point-scopes-allow` — Point out scopes that allow changes that can't be undone or that show personal data, the scopes your `auth.scope_hints` mark `irreversible` or with `personal_data`
- **SHOULD** · company · `guide.poppy-browser-sign` — When `poppy:browser-sign-in` allows everything the account can do on your website, say so in plain language, such as "Use the website as you, with full access to your account", and let the user leave it out while approving the rest (section 6)
- **SHOULD** · company · `guide.issuer-serves-several` — When your issuer serves several domains, `poppy:browser-sign-in` signs the browser in on each of them that lists a `browser_session_endpoint`. Name those websites when you ask the user to approve it, such as "Use example.com and example.co.uk as you" (3.2). If any of those websites is unscoped, describe the scope as full access and set `web.unscoped` on every domain (section 6)
- **SHOULD** · company · `guide.user-already-granted` — When the user already granted some of the scopes, show which ones are new, so the user doesn't review the whole list again. A personal agent that needs more access requests every scope it needs again (4.7)
- **SHOULD** · company · `guide.protect-page-against` — Protect the page against cross-site request forgery, and against framing by other sites with `Content-Security-Policy: frame-ancestors`
- **MUST** · company · `guide.redirect-exactly-match` — `redirect_uri` MUST exactly match an entry in the personal agent's `redirect_uris` (4.2)
- **SHOULD** · company · `guide.accept-pkce-s256` — Accept PKCE with `S256` only, and reject `plain`
- **SHOULD** · company · `guide.return-every-redirect` — Return `iss` in every redirect, success or error (4.2). Personal agents reject a redirect without it
- **SHOULD** · company · `guide.extra-protection-support` — For extra protection, support Pushed Authorization Requests (RFC 9126)
## guides.companies Device sign-in

- **SHOULD** · company · `guide.offer-direct-sign` — Offer direct sign-in too (SHOULD, 4). Device sign-in is easier to use for phishing

- **SHOULD** · company · `guide.user-confirm-code` — Ask the user to confirm that the code on the page matches the one the personal agent shows

## guides.companies Mediated sign-in

- **SHOULD** · company · `guide.rate-limit-attempts` — Rate-limit attempts by account, by `client_id`, and by network address, and cap wrong one-time codes
- **SHOULD** · company · `guide.require-time-code` — Require a one-time code when a sign-in looks unusual, including a personal agent's first mediated sign-in after the user disconnected it
- **SHOULD** · company · `guide.return-same-invalid` — Return the same `invalid_grant` error for an unknown account and a wrong password, so responses don't reveal whether an account exists
- **SHOULD** · company · `guide.never-store-credentials` — Never store raw credentials or codes, including in logs, traces, and idempotency records
- **SHOULD** · company · `guide.tell-user-example` — Tell the user, for example by email, when a personal agent signs in
## guides.companies Account settings

- **SHOULD** · company · `guide.account-settings` — In account settings, list each connected personal agent with its name, domain, scopes, and when it was last used
- **SHOULD** · company · `guide.offer-control-disconnect` — Offer a control to disconnect each one. Disconnecting revokes its refresh tokens, and its sessions continue signed out (5.5). Also invalidate the access tokens issued under them, as RFC 7009 §2.1 allows
## guides.companies Browser sessions

- **SHOULD** · company · `guide.endpoint-host-personal` — Put the endpoint on the host personal agents browse when you can. It can be on another host, such as `accounts.example.com`, as long as the session's cookie it sets reaches the pages personal agents browse (section 6)
- **SHOULD** · company · `guide.make-code-least` — Make each code at least 128 random bits, and expire it within 60 seconds
- **SHOULD** · company · `guide.cookie-ties-code` — Set the cookie that ties the code to the browser as `__Host-poppy_join=…; Path=/; Max-Age=60; Secure; HttpOnly; SameSite=Strict`, with `Max-Age` no longer than the code's lifetime. The `__Host-` prefix keeps other hosts on your domain from setting it, and `SameSite=Strict` keeps a form on another site from sending it (RFC 6265bis)
- **SHOULD** · company · `guide.send-page-cache` — Send the page with `Cache-Control: no-store`, `Content-Security-Policy: frame-ancestors 'none'`, and `Cross-Origin-Opener-Policy: same-origin`, so caches don't keep it, other pages can't frame it, and the page that opened it can't keep a reference to its window (section 6)
- **SHOULD** · company · `guide.answer-successful-form` — Answer a successful form with `303 See Other`, and a failed one with 400, or 429 when the browser sends too many requests
- **SHOULD** · company · `guide.endpoint-responses-request` — Don't log the endpoint's responses or request bodies. They contain browser-session codes
- **SHOULD** · company · `guide.keep-short-lived` — Keep a short-lived record for each code: whether it was authorized, for which session and account, and whether it was submitted. A store with a time to live of the code's lifetime works
- **SHOULD** · company · `guide.cookie-session-separate` — Use a cookie for the session that's separate from your login cookie, and check it first. After a signed-out join, keep the browser's login cookie. After a signed-in join, clear it, so the browser is signed out when the session's sign-in ends. Section 6 has a table of each case
- **SHOULD** · company · `guide.make-session-cookie` — Make the session's cookie `Secure` and `HttpOnly`, and use the `__Host-` prefix when the endpoint is on the host personal agents browse. When it's on another host, such as `accounts.example.com` for `www.example.com`, the cookie can't use `__Host-` and needs a `Domain` attribute. Set `Domain` to the narrowest domain that covers the hosts personal agents need, because `Domain=example.com` is sent to every subdomain, including one an attacker might take over. The join cookie is only read on the endpoint's host, so it keeps `__Host-` either way
- **SHOULD** · company · `guide.look-session-request` — Look up the session on each request, so sign-out and scope changes take effect on the website right away
## guides.companies Enforcing scopes everywhere

- **SHOULD** · company · `guide.apply-same-scope` — Apply the same scope rules on your website, APIs, company agent, and live agents. One shared check that every channel calls is easiest to keep consistent. Until your website can, let `poppy:browser-sign-in` stand for the account's full access there (Browser sessions)
- **SHOULD** · company · `guide.company-agent-tools` — Have the company agent's tools check the token's scopes on every call. Don't rely on the model to decide
- **SHOULD** · company · `guide.give-live-agents` — Give live agents' tools the same checks, so a person can't make a change the token doesn't allow (8.11)
- **SHOULD** · company · `guide.check-read-write` — Check read and write scopes separately. If a write scope also allows reading, say so in its description
- **SHOULD** · company · `guide.website-refuses-action` — When your website refuses an action for a missing scope, show an error that names the scopes (SHOULD, section 6)
## guides.companies Internal services

- **SHOULD** · company · `guide.forward-access-token` — Don't forward an access token or Session JWT from one of your services to another
- **SHOULD** · company · `guide.internal-services` — Verify them at the edge, then pass the verified `client_id`, session, user ID, account, and scopes to internal services through a gateway or service credentials
- **SHOULD** · company · `guide.internal-credentials-used` — Internal credentials used for a request shouldn't allow more than the access token does
## guides.companies Hosting several companies

- **SHOULD** · company · `guide.publish-metadata-issuer` — Publish metadata for each issuer at its own URL, such as `https://auth.platform.example/.well-known/oauth-authorization-server/outfitters` (3.2). Its `issuer` is the full issuer, and its `protected_resources` lists only that company's storefronts and resources, such as `https://outfitters.example`
- **SHOULD** · company · `guide.publish-protected-resource` — Publish protected resource metadata on each storefront's domain, with its company's issuer in `authorization_servers` (3.2)
- **SHOULD** · company · `guide.serve-storefront-poppy` — Serve each storefront's `poppy.json` on the storefront's own domain. A document redirected to the platform's domain speaks for the platform, not the storefront (3.1)
- **SHOULD** · company · `guide.companies-share-token` — Companies can share a token endpoint, servers, and signing keys. Only the issuer decides which company a token belongs to
- **SHOULD** · company · `guide.record-issuer-every` — Record the issuer with every session and token, and check it on every request. An access token, refresh token, or Session JWT for Outfitters must not work at Books, even when both are served by the same code
- **SHOULD** · company · `guide.company-records-another` — Don't use one company's records for another. A user's sessions, user IDs, and accounts at one company are unknown to every other company the platform hosts
## guides.companies A conversation endpoint at another provider

- **SHOULD** · company · `guide.list-conversation-endpoint` — List the conversation endpoint in `agent.protocols` in the company's `poppy.json`
- **SHOULD** · company · `guide.endpoint-service-resource` — Use that endpoint URL as the service's resource identifier, including the tenant path so tokens for different companies have different audiences (RFC 8707 §3). Publish its protected resource metadata at the URL RFC 9728 §3.1 defines:
- **SHOULD** · company · `guide.configure-company-issuer` — Configure the company's issuer to issue access tokens for that resource, with the scopes the conversation service uses. Publishing metadata alone doesn't configure the issuer or establish trust between the providers (RFC 8707 §2.2)
- **SHOULD** · company · `guide.personal-agent-discovers` — The personal agent discovers the resource and requests its access token from the company's issuer with `resource` set to the endpoint URL, at sign-in or refresh (4.5). The issuer can also list the resource in its `protected_resources` (3.2)
- **SHOULD** · company · `guide.arrange-conversation-provider` — Arrange for the conversation provider to validate access tokens from that issuer. For JWT access tokens following RFC 9068, use the issuer's metadata and signing keys and check the issuer, audience, expiry, and other validation rules. Another option is authenticated token introspection (RFC 7662). Enforce scopes and verify the Session header separately, including that the token was issued to the same client (5.3)
## guides.companies Offering personal agents less

- **SHOULD** · company · `guide.limit-scopes-grants` — Limit the scopes it grants by client, as OAuth allows (4.7). It can also leave scopes it doesn't offer personal agents out of `scopes_supported`, as RFC 8414 allows (3.2). When the issuer's metadata can't be tailored, such as a hosted issuer or one shared with other resources, list the scopes personal agents can request in `scopes_supported` of your protected resource metadata instead (4.7). These lists are discovery, not enforcement: agents can request scopes documented by an API or sign-in extension too
- **SHOULD** · company · `guide.refuse-sign-sign` — Refuse sign-in, or one sign-in type, to a personal agent with `unauthorized_client` from the grant's endpoint, and keep accepting it for signed-out sessions (4.1). `grant_types_supported` lists the grants every client can see, so a refusal by `client_id` is how you keep direct or device sign-in from some personal agents
- **SHOULD** · company · `guide.turn-sign-every` — Turn off sign-in for every personal agent with `auth.disabled`, for example while your issuer serves only other clients, or to keep one identifier across hostname changes before you offer sign-in (3.2). Personal agents don't try to sign in, and still use signed-out sessions. Remove it when you're ready
## guides.companies Conversations

- **SHOULD** · company · `guide.company-agent-everything` — Let your company agent do everything customers can do by phone, as fully as you can, so personal agents have no reason to call
- **SHOULD** · company · `guide.personal-agent-declares` — To a personal agent that declares the Links extension, send the pages a reply refers to as links, rather than URLs in `text`
- **SHOULD** · company · `guide.personal-agent-declares-2` — To a personal agent that declares the Disclosures extension, send notices users need to see, such as allergen or regulatory warnings, as disclosures, and keep them to those. Personal agents decide which to show, and skip ones that read like promotion. Without the extension, put the notice in `text`
- **SHOULD** · company · `guide.keep-what-message` — Keep what a message says in `text` and `data`, and use extension content to add to it, so a personal agent that ignores an extension still gets the message (8.4)
- **SHOULD** · company · `guide.write-whoever-other` — Write for whoever is on the other side (8.8). With a personal agent, skip greetings and small talk and keep text short. With the user, use plain sentences, a pace they can follow, and details in `text` rather than only in `data`. In a direct conversation, reply as you would to the customer on your own channels
- **SHOULD** · company · `guide.report-working-true` — Report `working` as `true` from the moment you accept a request until you've acted on it and finished replying, so a personal agent that reads until `working` is `false` gets the whole reply (8.7)
- **SHOULD** · company · `guide.request-company-agent` — Set `as_of_request` on each company agent message to the latest request the agent saw when it started the turn, and give the agent the `as_of_cursor` of each personal agent message, so it knows which of its messages a reply answers (8.4). Leave `as_of_request` off messages from people
- **SHOULD** · company · `guide.help-desk-withdraw` — If your help desk can withdraw a request for a person, do so on a handoff cancel, so no one is assigned to a conversation that no longer needs them (8.9)
- **SHOULD** · company · `guide.keep-conversation-events` — Keep a conversation's events for at least 30 days, so a personal agent that reconnects rarely hits `cursor_expired` (8.5)
- **SHOULD** · company · `guide.stream-nothing-send` — On a stream with nothing to send, send an SSE comment every 15 to 30 seconds, so proxies don't close it (8.6)
- **SHOULD** · company · `guide.session-signs-answer` — When a session signs out, answer requests without an access token on its conversations that used the account with a 401 challenge, including reads of their events, so their account details can't be read signed out (5.5, 8.11). Leave them open, so the user can sign in again and continue, or close them if your policy is to clear everything at sign-out
- **SHOULD** · company · `guide.before-closing-inactive` — Before closing an inactive conversation, say so in a message (8.12)
- **SHOULD** · company · `guide.send-authorization-event` — When you send an `authorization` event, also ask in a message, so a user in a direct conversation sees the request (8.11)
- **SHOULD** · company · `guide.sign-verify-user` — When sign-in can verify the user, send an `authorization` event (8.11) rather than asking for identifying details in messages, such as a date of birth, part of an account number, or a code sent by text. Sign-in proves who the user is, and it keeps codes and personal details out of messages and model context (Handling secrets)
- **SHOULD** · company · `guide.give-people-conversation` — Give the people a conversation is handed to (8.9) the same way to ask for sign-in, so they don't fall back to verification questions

- **SHOULD** · company · `guide.write-task-customer` — Write each task the way a customer would ask for it, such as "Send a wire transfer"
- **SHOULD** · company · `guide.give-alternative-whenever` — Give an alternative whenever there is one. Link to the page, or the screen in your app, where the user can do the task (9.2)
- **SHOULD** · company · `guide.serve-excluded-tasks` — Serve excluded tasks, skills, and your feedback endpoint from `tasks.endpoint` (section 9). If every Session gets the same response, you can cache it at your edge without verifying the Session header
- **SHOULD** · company · `guide.different-skills-alternatives` — To try different skills, alternatives, or feedback endpoints with some users, choose each Session's variant after verifying its Session header, and mark the response `private`. Choose by User ID to keep a user in the same variant across Sessions, or by Session ID to vary it from one Session to the next

## guides.companies Operations

- **SHOULD** · company · `guide.approval-actions-business` — Ask for approval for actions with a business effect that the user would want to confirm, such as ones that cost money or can't be undone. Don't ask for routine changes the user already asked for in so many words, such as updating a saved address
- **SHOULD** · company · `guide.everything-affects-action` — Put everything that affects the action in `terms`. Name its keys after the fields of the request or of your API's resources, such as `order_id`, so personal agents can compare them with what they asked for, and make each value clear on its own, such as an amount with its currency. Personal agents show `terms` to users, or describe them in their own words (Operations 3)
- **SHOULD** · company · `guide.send-summary-want` — Send a `summary` when you want users to read your wording. Write it so it stands alone: what will happen, to what, and any cost, date, or condition. Use bold for what matters most, such as the amount, and keep links out of it. Personal agents that show a summary show yours as is (Operations 3)
- **SHOULD** · company · `guide.openapi-description-endpoints` — Say in your OpenAPI description which endpoints can return `approval_required` or `approval_declined` (Operations 4)
- **SHOULD** · company · `guide.approval-user-approval` — An approval is a user approval, or an agent approval on the user's instruction, and says which in `approver`. Record `approver` and `reference` with the operation, so you can look into an approval with the personal agent's operator later (Operations 8.1)
- **SHOULD** · company · `guide.actions-where-want` — For actions where you want to see the user approve, don't return operations. Handle them on your website or in your app until signed user approvals exist (roadmap)
- **SHOULD** · company · `guide.choose-expires-kind` — Choose `expires_at` for each kind of action. Give the user at least 15 minutes, and longer for terms that don't change, such as cancelling a subscription at the end of the month. Keep it short when you hold something for the user, such as a seat or a sale price. If you don't store operations, you can't hold a price: an approval that arrives after the price changed gets a new revision (Operations 3)
- **SHOULD** · company · `guide.keep-record-performed` — Keep your record of a performed operation until its approved revision expires, and no longer than you need to. A store with a time to live set from `expires_at` works (Operations 7)
- **SHOULD** · company · `guide.avoid-storing-operations` — To avoid storing operations nobody has approved, compute them from the request (Operations 3). Give a request without an approval a new random `operation_id`, such as `exc_5Rt2`, so a user can repeat an action on purpose. When a request with an approval no longer matches, return the new revision with that approval's `operation_id`. In a conversation, keep the `operation_id` when the user asks for different terms
- **SHOULD** · company · `guide.compute-operations-make` — When you compute operations, make the `revision` the expiry as a Unix time and an HMAC-SHA256, with a key kept like your other signing keys, over the `operation_id`, the expiry, the terms in a canonical form such as RFC 8785 whether or not you return `terms`, and who can approve it: the `client_id`, the User ID, and the account when signed in. Include the method, URL, and the parts of the body or tool arguments that affect the action. Leave out the `summary`, so you can reword it
- **SHOULD** · company · `guide.request-comes-back` — When the request comes back with an approval, compute the terms again from your current data, such as today's price, then the HMAC. Compare it in constant time and check the expiry. If the price or anything else changed, the HMAC doesn't match, and you return a new revision for the current terms. The revision only shows that the terms changed: always use your current price. If you store operations instead, store each revision's terms with such a fingerprint of the request, so you can check that a request with an approval asks for exactly what was approved (Operations 6)
- **SHOULD** · company · `guide.call-another-system` — When you call another system to perform the action, such as a payment processor or a warehouse, derive its idempotency key from the operation ID. A retry then can't perform the action twice downstream either
- **SHOULD** · company · `guide.downstream-call-times` — If a downstream call times out, ask that system whether the action happened, using your business reference, before trying again. Until you know, answer retries with 503 and `Retry-After` (Operations 7)
- **SHOULD** · company · `guide.keep-record-approval` — Keep a record of each approval: the operation, revision, `client_id`, account, and time. It shows what the personal agent stated the user approved (Operations 8.1)
- **SHOULD** · company · `guide.approval-website-make` — To ask for approval on your website, make the reference in `Poppy-Operation` a sealed copy of the operation and the request's fingerprint, such as a JWS or an HMAC over who can approve it as for the `revision`, so you don't store operations nobody approved (Operations 4)
- **SHOULD** · company · `guide.keep-recorded-approvals` — Keep recorded approvals in the store you use for performed operations, by the account, or by the personal agent's `client_id` and User ID when signed out, with a time to live set from `expires_at`. One record can go from approved to performing to performed (Operations 6)
- **SHOULD** · company · `guide.browser-repeats-request` — When the browser repeats the request, check it against each unused approval recorded for that account or user as you would check a request that carries the approval: compute the terms and the HMAC again with the approved revision's `operation_id` and expiry. Mark the approval used when you perform the action, so a later request gets a new operation
- **SHOULD** · company · `guide.page-waiting-tell` — On the page that's waiting, tell the user the action needs their approval in their personal agent, and offer a Continue button that makes the original request again. A page that polls your own status endpoint can repeat the request itself once the approval is recorded. Don't use operations on the website for an action you can't repeat, such as one behind a single-use form token. Handle its approval yourself instead. Send `Poppy-Operation` on the response to the request itself, including a script's `fetch`, so it works for buttons as well as forms
- **SHOULD** · company · `guide.make-sure-application` — Make sure your CDN or web application firewall passes a 403 with `Poppy-Operation` through unchanged. Some replace the body of error responses with their own page or drop headers, and the personal agent then can't find the operation (Operations 4)
